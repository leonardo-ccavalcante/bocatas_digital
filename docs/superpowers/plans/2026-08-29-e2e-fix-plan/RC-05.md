# RC-05 — Check-in: queue transport failures as offline and surface the paused offline state in manual search

> Part of [2026-08-29 E2E fix plan](../2026-08-29-e2e-fix-plan.md). **REQUIRED SUB-SKILL:** use `superpowers:subagent-driven-development` or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Severity:** high · **Status at HEAD:** open · **Estimate:** 55 min · **Findings:** F028, F029

**Goal:** On /checkin, a check-in whose request dies in transit while navigator.onLine is still true (weak signal, captive portal, server restart) is queued offline exactly like an airplane-mode check-in instead of being lost behind an English "Failed to fetch" card (F028); a genuine server 500 shows generic Spanish text instead of raw DB error text (F028); and the manual-search modal tells the volunteer in Spanish that name search needs internet instead of rendering nothing when react-query pauses the query offline (F029).

**Rationale:** Root cause: useCheckin.ts keys offline handling solely on navigator.onLine (lines 105-120 and the onError at 141-159), which stays true on weak/captive networks — the real counter condition — so transport failures bypass the queue and err.message (browser English or server-embedded DB text) is sent verbatim to ResultCard, violating the Spanish-only UI rule. ManualSearchModal.tsx (lines 25-28, render branches 69/85/135/143) never reads fetchStatus, and react-query's default networkMode pauses the query offline with isLoading=false and data=undefined, so NO branch matches and the modal is silently dead. The reliable discriminator on the client is TRPCClientError.data: a response that never arrived carries no server-sent data (data == null), while any real server reply (400/404/500) carries data.code. Fixing this unblocks the core counter flow at /checkin: offline-queued check-ins for named + anonymous paths under flaky networks, and a comprehensible manual-search offline state. ResultCard.tsx needs no change because the message is mapped to Spanish before the ERROR event is sent.

// ── Error classification (F028) ──────────────────────────────────────────────
// navigator.onLine stays true on weak signal / captive portals, so a request
// that dies in transit reaches onError while `isOnline` is still true. A tRPC
// client error that carries no server-sent `data` never got a server response
// (browser "Failed to fetch", DNS failure, aborted socket) — treat it exactly
// like being offline and queue the check-in instead of losing it.
type CheckinClientError = { message: string; data?: { code?: string } | null };

function isTransportError(err: CheckinClientError): boolean {
  return err.data == null;
}

// Spanish-only UI: never surface raw DB/browser text to the volunteer.
// Non-500 server errors (BAD_REQUEST, NOT_FOUND…) already carry Spanish
// messages written by our routers, so pass those through.
function checkinErrorMessage(err: CheckinClientError): string {
  return err.data?.code === "INTERNAL_SERVER_ERROR"
    ? "No se pudo registrar el check-in. Inténtalo de nuevo."
    : err.message;
}

## ADR notes

ADR-0003 (XState only for check-in): respected — the fix reuses the existing OFFLINE/ERROR machine events and adds no new states or machines. Spanish-only UI chrome rule: this fix is what brings the error path into compliance (browser/DB English no longer reaches the volunteer). ADR-0001 (Zod single source): untouched — no schema changes. No ADR conflicts. Detection uses TRPCClientError's data==null contract (no server response) rather than string-matching 'Failed to fetch', so it is locale- and browser-independent.

1) "checkin.verifyAndInsert: stop embedding raw DB error text (insertError.message) in TRPCError messages" — server/routers/checkin.ts:195-199 still ships DB internals to every client; this task only stops displaying them (server file is outside RC-05's lane here). 2) "Offline manual search: cache a local roster of recent/frequent persons so name search works with zero connectivity" — the paused-state hint is honest but QR/anonymous remain the only fully offline paths; needs a product + EIPD-scope decision (PII persisted on shared counter devices). 3) "ResultCard error state: offer a 'Reintentar' action that re-fires verification without re-searching" — today RESET returns to idle and the volunteer must search again after a genuine server error.
