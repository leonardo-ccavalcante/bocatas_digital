# RC-08 — families search: filter the embedded titular with !inner + or() scoped to the persons embed; render titular_nombre/estado and error states in the clients

> Part of [2026-08-29 E2E fix plan](../2026-08-29-e2e-fix-plan.md). **REQUIRED SUB-SKILL:** use `superpowers:subagent-driven-development` or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Severity:** high · **Status at HEAD:** open · **Estimate:** 90 min · **Findings:** F072, F073, F160, F165, F186, F203

**Goal:** Make every families text search actually work: families.getAll name search must return HTTP 200 with only matching families (today any non-numeric search is a PGRST100 parse error surfaced as HTTP 500 — F073/F160/F203: Familias tab search, Derivar typeahead, UploadModal family picker are all dead), and families.verifyIdentity must return only the families whose titular matches (today it returns the first 5 active families with titular_nombre "" for ANY name — F072/F165/F186: a volunteer verifying identity at the counter is shown the wrong family). Also fix the two client mismatches the same findings exposed: /familias/verificar renders fields the procedure never returns (persons?.nombre, estado) and blocks single-digit family-number searches, and FamiliasList silently shows nothing on a query error.

**Rationale:** PostgREST semantics (verified live against the local stack in this session): (1) a filter on an embedded resource without !inner only NULLS the embed — parent rows are NOT filtered, which is exactly the verifyIdentity behaviour (compliance.ts:103 `.ilike("persons.nombre", …)` on a plain `persons!titular_id(...)` embed → LIMIT 5 over all active families); (2) embedded dotted paths inside a TOP-LEVEL `or=` are a PGRST100 parse error, which is exactly the getAll 500 (crud.ts:76-78). The correct shape — `persons!titular_id!inner(...)` in the select plus `.or("nombre.ilike.…,apellidos.ilike.…", { referencedTable: "persons" })` — was probed against the running local PostgREST in this session and returns 0 rows for a no-match query and correctly-joined titulars for matches. The !inner embed is applied ONLY on the name-search branch so the plain list and numeric search keep left-join semantics (families with NULL titular_id — the column is nullable — still appear). shared/postgrestFilter.ts needs NO change: ilikeForOr is already the correct escaper for values embedded in an .or() list (the existing ilikeValue call in compliance.ts is replaced by ilikeForOr because the value moves into an or= list). Numeric search working all along is what masked this in earlier QA.
