# RC-02 — Re-grant service_role EXECUTE on the three SECURITY DEFINER RPCs, drop the broken get_user_role() gate from upload_family_document, and surface duplicate-check degradation in the wizard

> Part of [2026-08-29 E2E fix plan](../2026-08-29-e2e-fix-plan.md). **REQUIRED SUB-SKILL:** use `superpowers:subagent-driven-development` or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Severity:** high · **Status at HEAD:** open · **Estimate:** 90 min · **Findings:** F025, F048, F251, F157, F204

**Goal:** Make persons.findDuplicates (F025/F048/F251, route /personas/nueva), families.uploadFamilyDocument (F157 route /familias/:id tab Documentación; F204 route /programas/programa_familias?tab=uploads) and announcements bulk-confirm (part of F204's cluster) work again by granting service_role EXECUTE on public.find_duplicate_persons, public.confirm_bulk_announcement_import and public.upload_family_document, and by replacing upload_family_document without its always-failing get_user_role() gate and without its 42804 text→uuid insert. Additionally, stop the registration wizard from silently swallowing duplicate-check failures: expose isDegraded from useDuplicateCheck and render a non-blocking Spanish notice in phase 1.

**Rationale:** Migration 20260506000007 executed `REVOKE EXECUTE ON FUNCTION %s FROM PUBLIC, authenticated` over all SECURITY DEFINER functions, claiming in its header that "service_role retains EXECUTE". That claim is false for these three functions: they were only ever granted TO authenticated (20260411181059:49, 20260501132517:95, 20260430000005:64) and service_role relied on the PUBLIC default, so the revoke left service_role with NO grant. Verified at HEAD via psql: has_function_privilege('service_role', …, 'EXECUTE') = f for all three. Every createAdminClient().rpc() call therefore fails 42501 → generic 500: duplicate detection is dead on every keystroke of /personas/nueva (and useDuplicateCheck coerces the error to [], so duplicates are silently creatable — F048), family document upload always fails, bulk announcement confirm always fails. upload_family_document has two further layers that make a grant alone insufficient: (a) its get_user_role() gate reads auth.jwt(), which is always absent under the service-role client, so it raises 'Forbidden' for every legitimate caller (F204); (b) it inserts p_verified_by TEXT directly into the uuid column verified_by (FK → auth.users.id), which raises 42804 in PL/pgSQL — confirmed by runtime probe. Per ADR-0002 the tRPC adminProcedure (server/routers/families/documents.ts:161) is the enforcement boundary, so the in-function gate is both broken and redundant; the reconciliation instructs landing the verified_by resolution in the same replaced body (RC-42's DB layer). This is the exact AGENTS.md "SECURITY DEFINER functions — DROP+CREATE loses grants" landmine, fixed the way that doc prescribes: an explicit GRANT EXECUTE … TO service_role at the end of the migration.

```sql
-- 20260830000001_grant_service_role_secdef_rpcs.sql
--
-- RC-02 (QA findings F025/F048/F251/F157/F204): 20260506000007 revoked EXECUTE
-- FROM PUBLIC, authenticated on the SECURITY DEFINER RPCs, claiming
-- "service_role retains EXECUTE". False for these three: they were only ever
-- granted to `authenticated` (20260411181059, 20260501132517, 20260430000005)
-- and service_role relied on the PUBLIC default that the revoke removed. Every
-- createAdminClient().rpc() call has failed 42501 since: persons.findDuplicates
-- 500s on every keystroke, families.uploadFamilyDocument and the announcements
-- bulk-confirm always fail.
--
-- Fix 1: explicit GRANT EXECUTE ... TO service_role for the three functions
--   (AGENTS.md "SECURITY DEFINER functions — DROP+CREATE loses grants").
--   Deliberately NOT re-granted to anon or authenticated: the browser never
--   calls these RPCs; tRPC procedure guards are the PII/authz wall (ADR-0002).
--
-- Fix 2: CREATE OR REPLACE upload_family_document WITHOUT the
--   public.get_user_role() gate added in 20260430000005. get_user_role() reads
--   auth.jwt(), which is absent under the service-role client (identity comes
--   from the app layer per ADR-0002), so the gate raised 'Forbidden' for every
--   legitimate caller. Authorization now lives solely in the tRPC
--   adminProcedure (server/routers/families/documents.ts uploadFamilyDocument)
--   — guard removal recorded here on purpose.
--   The replaced body also resolves p_verified_by (TEXT, an app-layer actor id
--   that may be non-UUID, e.g. the dev session id) against auth.users:
--   verified_by is uuid with an FK to auth.users(id), and the previous direct
--   insert of a TEXT value raised 42804 on every call.
--
-- CREATE OR REPLACE (never DROP) so the ACL is preserved; the explicit
-- service_role grant at the end re-asserts it regardless.

BEGIN;

-- Fix 1 — existence-tolerant re-grant (same DO-block shape as 20260506000007).
DO $$
DECLARE
  fn_signature text;
  fn_signatures text[] := ARRAY[
    'public.find_duplicate_persons(text, text, double precision)',
    'public.confirm_bulk_announcement_import(uuid, text, text)',
    'public.upload_family_document(uuid, integer, uuid, text, text, text)'
  ];
BEGIN
  FOREACH fn_signature IN ARRAY fn_signatures LOOP
    BEGIN
      EXECUTE format('GRANT EXECUTE ON FUNCTION %s TO service_role', fn_signature);
    EXCEPTION WHEN undefined_function THEN
      RAISE NOTICE 'skip GRANT on %: not present in this DB', fn_signature;
    END;
  END LOOP;
END $$;

-- Fix 2 — replace upload_family_document (same signature, no role gate).
CREATE OR REPLACE FUNCTION public.upload_family_document(
  p_family_id UUID,
  p_member_index INTEGER,
  p_member_person_id UUID,
  p_documento_tipo TEXT,
  p_documento_url TEXT,
  p_verified_by TEXT
)
RETURNS family_member_documents
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
DECLARE
  v_inserted family_member_documents;
  v_verified_by uuid;
BEGIN
  -- p_verified_by is the app-layer actor id and may be non-UUID (Manus openId,
  -- dev session id). verified_by is uuid with FK -> auth.users(id): resolve to
  -- a real auth user or NULL instead of raising 42804/22P02/23503.
  SELECT u.id INTO v_verified_by
    FROM auth.users u
   WHERE u.id::text = p_verified_by;

  -- Mark prior current row(s) as not-current. Locks the rows for this
  -- family+member+doc_type.
  UPDATE family_member_documents
     SET is_current = false
   WHERE family_id = p_family_id
     AND member_index = p_member_index
     AND documento_tipo = p_documento_tipo
     AND deleted_at IS NULL
     AND is_current = true;

  -- Insert the new current row.
  INSERT INTO family_member_documents (
    family_id, member_index, member_person_id,
    documento_tipo, documento_url,
    fecha_upload, verified_by, is_current
  )
  VALUES (
    p_family_id, p_member_index, p_member_person_id,
    p_documento_tipo, p_documento_url,
    now(), v_verified_by, true
  )
  RETURNING * INTO v_inserted;

  RETURN v_inserted;
END;
$$;

-- AGENTS.md rule: every convergence migration touching a SECURITY DEFINER
-- function ends with an explicit service_role grant.
GRANT EXECUTE ON FUNCTION public.upload_family_document(UUID, INTEGER, UUID, TEXT, TEXT, TEXT) TO service_role;

COMMENT ON FUNCTION public.upload_family_document(UUID, INTEGER, UUID, TEXT, TEXT, TEXT) IS
  'Atomic version-rollover for family_member_documents. '
  'Marks the prior is_current=true row as not-current, then inserts a new current row. '
  'Authorization: tRPC adminProcedure (ADR-0002); EXECUTE granted to service_role only. '
  'verified_by resolves p_verified_by against auth.users; NULL when the actor id is not an auth user. '
  'Concurrency: a simultaneous second call may trigger unique_violation from the INSERT — '
  'acceptable for single-device-per-session Bocatas workflows.';

COMMIT;
```

```ts
/**
 * useDuplicateCheck — hook that checks for potential duplicate persons.
 *
 * Calls trpc.persons.findDuplicates (server-side, createAdminClient =
 * service_role) because the find_duplicate_persons RPC has EXECUTE revoked
 * from PUBLIC/authenticated/anon (migrations 20260506000007, 20260613000001).
 * service_role's own EXECUTE is granted explicitly in 20260830000001 — it was
 * never implicit (RC-02).
 *
 * Graceful degradation is EXPLICIT, never silent: on error `data` stays []
 * so the registration wizard is not blocked, and `isDegraded` is true so the
 * phase-1 step renders a non-blocking notice telling the volunteer the
 * duplicate check did not run (see Step1Identidad).
 */
import { trpc } from "@/lib/trpc";
import type { DuplicateCandidate } from "../schemas";

const SIMILARITY_THRESHOLD = 0.70;

export function useDuplicateCheck(
  nombre: string,
  apellidos: string,
  enabled = true
) {
  const fullName = `${nombre.trim()} ${apellidos.trim()}`.trim();

  const query = trpc.persons.findDuplicates.useQuery(
    {
      nombre: nombre.trim(),
      apellidos: apellidos.trim(),
      threshold: SIMILARITY_THRESHOLD,
    },
    {
      enabled: enabled && fullName.length >= 4,
      staleTime: 30_000,
      retry: false,
    }
  );

  return {
    ...query,
    data: (query.data ?? []) as DuplicateCandidate[],
    isDegraded: query.isError,
  };
}
```
