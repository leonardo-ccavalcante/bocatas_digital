# RC-04 — Offline check-in queue: stop persisting isSyncing, move flush callbacks to useMutation level, add manual Reintentar

> Part of [2026-08-29 E2E fix plan](../2026-08-29-e2e-fix-plan.md). **REQUIRED SUB-SKILL:** use `superpowers:subagent-driven-development` or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Severity:** high · **Status at HEAD:** open · **Estimate:** 50 min · **Findings:** F026, F033

**Goal:** Queued offline check-ins must always reach the server: a reload mid-flush must never leave the queue frozen on "Sincronizando..." (F026), navigation during a flush must never strand isSyncing:true (F026), and items whose sync failed must be retryable by the volunteer via a "Reintentar" button instead of waiting for connectivity to flap (F033). Route: /checkin.

**Rationale:** Three compounding defects share one root cause — transient sync state treated as durable and lifecycle callbacks tied to component mount. (1) useCheckinStore uses zustand persist with NO partialize, so the transient isSyncing flag is written to localStorage; after a reload mid-flush the rehydrated isSyncing:true makes the flush guard at useCheckin.ts:166 early-return forever — queued attendances silently never reach the DB and only clearing site data recovers (F026, verified at HEAD: store lines 92-108 have version:4, no partialize, no v5 migrate). (2) The only code that clears isSyncing lives in mutate()-level callbacks (useCheckin.ts:170-186), which TanStack Query v5 skips when the observing component unmounted mid-flight — same stuck state without touching localStorage. (3) The flush effect deps are [isOnline, offlineQueue.length] (line 187); failed items stay in the queue (length unchanged) so nothing ever retries them, and OfflinePendingBadge is display-only. Fix: partialize + migrate v5 in the store; mutation-level onSuccess/onError/onSettled in the hook; expose retrySync and wire a "Reintentar" button on the badge. server/routers/checkin.offlineSync.ts was inspected and needs no change (it already returns per-item statuses; the loss happens client-side). No automatic retry loop is added on purpose — a tight fail→markFailed→re-flush loop is the hazard the current deps accidentally avoid; the deliberate backoff design is a follow-up.

      )}
    </div>
  );
}
