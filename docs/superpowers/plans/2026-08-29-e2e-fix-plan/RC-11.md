# RC-11 — Renuncia revert: re-registering contact must reset attended to NULL so the family reappears in rosters

> Part of [2026-08-29 E2E fix plan](../2026-08-29-e2e-fix-plan.md). **REQUIRED SUB-SKILL:** use `superpowers:subagent-driven-development` or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Severity:** high · **Status at HEAD:** open · **Estimate:** 35 min · **Findings:** F185

**Goal:** Make the renuncia reversal the ContactoFamiliaDialog already promises ("Puede revertirse volviendo a registrar el contacto") actually work: when a contact outcome other than 'renuncia' is recorded over an assignment whose stored estado_contacto is 'renuncia', reset attended, attended_slot_id, attended_at and attended_by to NULL so the family is pending again and reappears in getSlotRoster's Pendientes on every open day (F185, route /programas/programa_familias?tab=repartos, gh #129).

**Rationale:** F185: buildContactoOutcomeUpdate (server/routers/families/contacto-outcome.ts:36-48) stamps attended=false on renuncia but its non-renuncia branch spreads `{}`, so re-registering contact leaves attended=false with attended_slot_id=NULL. getSlotRoster (rounds-closeout.ts:64-79) lists pending as attended===null and attended_here by attended_slot_id===slot, so the reverted family is listed and counted NOWHERE ('3 pendientes · 0 atendidas · 0 ausentes'), and renuncia writes nothing to undo_log so Deshacer cannot help either. Because contacto-outcome.ts is the single shared write for BOTH the admin mutation (rounds-contacto.ts setContactoFamilia) and the n8n inbound webhook (reparto-contacto-inbound.ts), fixing the builder — fed with the previously stored estado_contacto by each call site — fixes both entry points at once. The reset is deliberately gated on previousEstado==='renuncia' so a contact re-registration can never wipe a real attendance (attended=true) recorded at close-out; after a renuncia, attended is always false (renuncia'd rows are excluded from rosters and resolveAssignment returns 'ausente', so no attendance can be stacked on top). rounds-closeout.ts needs NO change — its classification is correct once attended is back to NULL. No DB change: all attended* columns are already nullable in delivery_round_assignments.

```ts
// MYTHOS: MYT-129B (gh #129)
//
// Shared "apply a contacto outcome" write, used by BOTH the admin mutation
// (rounds-contacto.ts's setContactoFamilia) and the n8n inbound webhook
// (reparto-contacto-inbound.ts). Before this file existed the two call sites
// hand-rolled the same write independently and already diverged once — the
// renuncia-clears-preferred bug fixed in #125. Pinning the derivation here
// means a future edit to one call site can no longer silently re-diverge from
// the other.
import type { SupabaseClient } from "@supabase/supabase-js";
import type { Database } from "../../../client/src/lib/database.types";
import type { EstadoContacto } from "../../../shared/repartoSchemas";

type AssignmentsUpdate = Database["public"]["Tables"]["delivery_round_assignments"]["Update"];

export interface ContactoOutcomeInput {
  assignmentId: string;
  estado: EstadoContacto;
  preferredSlotIds: string[];
  actor: string;
  /**
   * The assignment's estado_contacto as stored BEFORE this write (the caller
   * reads it in the same request). Required so a non-renuncia outcome recorded
   * over a stored 'renuncia' clears the ausente stamp — the reversal the
   * contact dialog promises (F185, gh #129) — while a re-contact over any
   * other estado never touches the attended fields.
   */
  previousEstado: string | null;
}

/**
 * The single source of truth for what a contacto outcome writes: a renuncia is
 * derived from `estado` (never a separate flag) and ALWAYS clears
 * preferred_slot_ids + stamps the assignment ausente — even if the caller
 * still holds stale preferred ids. Conversely, a non-renuncia outcome over a
 * stored 'renuncia' resets attended/attended_slot_id/attended_at/attended_by
 * to NULL so the family is pending again on every open day's roster.
 * Exported standalone so a call site that must merge extra columns into the
 * same single UPDATE (e.g. the n8n inbound handler's reschedule_log) can
 * still share this exact derivation.
 */
export function buildContactoOutcomeUpdate({
  estado,
  preferredSlotIds,
  actor,
  previousEstado,
}: Omit<ContactoOutcomeInput, "assignmentId">): AssignmentsUpdate {
  if (estado === "renuncia") {
    return {
      estado_contacto: estado,
      preferred_slot_ids: [],
      attended: false,
      attended_slot_id: null,
      attended_at: new Date().toISOString(),
      attended_by: actor,
    };
  }
  // Reverting a renuncia ("puede revertirse volviendo a registrar el
  // contacto"): reset the ausente stamp so getSlotRoster's pending filter
  // (attended IS NULL) lists the family again (F185, gh #129). Any other
  // previous estado leaves the attended fields untouched — a re-contact must
  // never wipe a real attendance recorded at close-out.
  return {
    estado_contacto: estado,
    preferred_slot_ids: preferredSlotIds,
    ...(previousEstado === "renuncia"
      ? { attended: null, attended_slot_id: null, attended_at: null, attended_by: null }
      : {}),
  };
}

/**
 * Applies the shared outcome write for one assignment. Returns the
 * still-chainable update query so a caller can tack on its own
 * `.select(...).single()` for its own response shape — the write itself is
 * defined in exactly one place.
 */
export function applyContactoOutcome(db: SupabaseClient<Database>, input: ContactoOutcomeInput) {
  return db
    .from("delivery_round_assignments")
    .update(buildContactoOutcomeUpdate(input))
    .eq("id", input.assignmentId);
}
```

## ADR notes

ADR-0016 §5 (renuncia = ausente) is preserved: a renuncia still stamps attended=false immediately; only the explicitly UI-promised revert path (a subsequent non-renuncia contact outcome) clears the stamp, and only when the stored estado was 'renuncia', so a re-contact can never erase a real close-out attendance. ADR-0005 untouched (webhook change is read-one-more-column only). No schema change, so ADR-0001/Zod schemas and database.types.ts stay as-is. No UI change needed: ContactoFamiliaDialog.tsx's copy ('Puede revertirse volviendo a registrar el contacto') becomes true instead of being removed, and CloseoutDayView/getSlotRoster classification already handles attended=NULL correctly.

## Deliberately NOT done (follow-ups)

Renuncia appends nothing to undo_log, so 'Deshacer' in Cierre por día cannot restore a renuncia'd assignment — needs an atomic append (RPC or read-modify-write) into undo_log at renuncia time. Also worth adding: a DB-gated integration test (RUN_LOCAL_SUPABASE_TESTS=true) asserting the reverted family reappears in getSlotRoster.pending end-to-end, alongside rounds-closeout-integrity.integration.test.ts.
